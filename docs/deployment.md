# Deployment context

Current as of October 31, 2026. This is the active public repository context following publication and production cutover. Earlier preparation holds describe history unless repeated below.

## Source and deployment ownership

The canonical public repository's protected `main` branch deploys the live cockpit at [gtm.vibrana.ai](https://gtm.vibrana.ai) through Vercel project `vibrana-gtm`. Develop and open PRs here. The old private archive preserves history and unfinished work; all of its GitHub Actions are disabled. Do not resume development or CI there.

Required CI and independent exact-head review remain release gates. A merge to `main` is a live deployment. Preserve the prior production deployment and its configuration until the replacement passes the applicable runtime and authorization checks. Use the approved provider promotion/rollback route, never a Vercel CLI deployment.

## Production and previews

Canonical production runs with `CONTENT_MODE=private` and `DEMO_MODE=0`. Its guide and typed operational configuration come from separately reviewed private data. Production credentials and private data do not enter public CI or previews.

Preview deployment execution is disabled on the real production project. Public PR previews run on the separate sample project, `vibrana-gtm-public-preview`. That project's production publication remains held by `publication-production-held`; the hold does not describe the canonical live application.

Local/public CI defaults to samples. The dedicated demo additionally blocks live provider operations and uses its own local database. Neither sample guide content nor sample account/catalog/mail settings are production authority.

## Build and private delivery

The production provider runs:

```sh
node scripts/production-install.mjs
node scripts/production-build.mjs
```

Installation removes restored private caches and disables dependency lifecycle scripts during a full frozen-lockfile install with a scrubbed environment. The trusted build validates provider identity before fetching the private artifact, verifies every data pin and materializes only validated bytes for server runtime. Environment scrubbing is not an operating-system sandbox.

The operated delivery path is HTTPS from an authenticated, static data-only project. Its immutable artifact contains nineteen guide/voice/season JSON members, the overlay manifest and a separate typed runtime JSON file. The project requires authentication on every deployment. A project-scoped protection-bypass credential travels only in a request header; it is effectively read-only because the project has no executable or write endpoints. It is not a provider-management credential or a hub-read token.

The source retains an optional SSH transport, but organization policy disables deploy keys. Do not weaken that policy or treat SSH as the active setup. See [private data loading](private-overlay.md) for schemas and pin names. Actual private values, artifact addresses and credentials belong in protected deployment configuration, not public documentation.

The generated release stamp binds the actual provider repository, project, protected branch, Git SHA and deployment ID to the immutable data revision/digests. Runtime rejects a mismatch. Each normal protected-main deployment receives its own stamp, so routine source merges need no manual per-head environment update. `PRIVATE_RELEASE_SHA` is intentionally unset in the operated deployment; configuring it would add a manual constraint.

## Database, authorization and schedules

Existing Supabase configuration and owner/team/reviewer claim boundaries remain in force. The website repository owns production schema; the vendored migration snapshot supports isolated local tests and demos. Do not reset production, import sample data or replay sanitized history as a cutover step.

The Vercel cron routes are configured in `vercel.json` (eleven, with the pipeline, YouTube and CRM mirror crons); retain their authentication and provider approval boundaries. This cutover does not authorize a test email, campaign or duplicate scheduled job.

`/api/cron/crm-mirror` (hourly at :05) keeps `gtm_crm_people`, the cockpit's copy of every Twenty person (VIB-516): ids, dates and status flags only. No person's name, address, phone or text is stored; the creator's Twenty member name or API key name is kept, because team attribution uses it. It skips the run unless Twenty's `/healthz` answers 200, holds the `crm.mirror` lease, reads 100 people a page 1.5 s apart, and reads only what changed since its cursor plus people soft-deleted since then. Each pass starts just after the last change it saw, or 10 minutes before the earliest page of the previous pass that was reading changes from the last 10 minutes, so a write that committed out of order is still read and settled history is never re-read. It saves its place after every page, so the first backfill (about 140 pages for 14k people) spans one or two runs. When more people than a page share one millisecond (a bulk update), Twenty's cursor cannot move past them, so the mirror reads that millisecond by id, saving its place after every page (a bulk update bigger than one run resumes next run), and carries on. A run that reads nothing before its deadline counts as a failure. If the counts still disagree after a resync, it raises an incident and resyncs at most once a day. Once caught up it compares people created more than 10 minutes before the run, in Twenty and in the mirror; the same difference on two checks in a row starts a resync (every person read again, about 140 pages) and an id sweep for erased rows (about 140 more pages), which refuses to remove more than half of a page's range at once. State: `gtm_sync_state` key `crm.people.mirror`. The team run (:20) counts people from the mirror and reports them as not measured, with the reason, until the backfill has finished, while the sweep is held, after 6 hours without a healthy run, or after 24 hours without catching up; the member's other numbers are still saved.

Problems become health incidents (emailed once to `EMAIL_ALERT_TO`, resolved when they clear): no healthy run for 6 hours (including a mirror whose every run fails, with its last error), no catch-up for 24 hours, or the sweep stopped by its breaker. A run that ends on an error answers 500 in the cron log. **Recovering from a breaker stop:** first check in Twenty that people really were not mass-deleted (if they were, restore them from Twenty's trash or the nightly backup before anything else). Once the CRM is right, clear the hold so the next run sweeps again: `update gtm_sync_state set value = value || '{"sweepError": null, "sweep": {"after": null, "lastId": null, "removed": 0}}' where key = 'crm.people.mirror';`. To start the mirror over completely, run `delete from gtm_crm_people;` and `delete from gtm_sync_state where key = 'crm.people.mirror';` together (deleting only the state leaves erased people live in the table); the next runs copy the CRM again.

`/api/cron/pipeline` (hourly at :50) stores the pipeline dashboard's numbers: the first time each opportunity is seen at a stage, reply and bounce outcomes for accepted client-stream desk emails from the HQ outreach mailbox (read-only; guest and network emails go from other mailboxes and are not read), `lastContactedAt` on the Twenty people the desk emailed on any stream (the cockpit's one Twenty write, forward-only; a LinkedIn note sets it only on the network stream), and one finished day of site traffic per site from the Vercel Web Analytics API. Each step is nonfatal and reports its own result. Site traffic needs `VERCEL_ANALYTICS_TOKEN`, `VERCEL_TEAM_ID` and `VERCEL_ANALYTICS_SITES` in production; without them the Traffic tab says it is not connected. Wise reconciliation of payment milestones is local only (`gtm sales reconcile`).

**Team mailbox incidents.** A mailbox's `last_error` becomes a `collection:` incident. One that needs a person (reconnect, wrong account) is raised on the first failed run; one that says it retries or resumes next hour is raised only from the second failed run in a row (the streak is `gtm_sync_state` key `team.mailbox.<member>.h<hash>.failures`, cleared by the next successful run). Reconnecting a mailbox loses nothing: it clears the cursor, so the next runs list sent mail again from the backfill start and re-read outreach threads, and the calendar re-reads its 60-day window every run.

### Origami opt-outs (VIB-521)

Origami has no global suppression: its exclusion list blocks no API enrollment and an "Unsubscribe" reply stops only that one sequence. The team run (`/api/cron/team`, hourly at :20) and the webhook `/api/webhooks/origami` carry Origami opt-outs into Twenty and stop the person in every Origami campaign. Both are off until `ORIGAMI_OPTOUT_APPLY=1`.

- **Order in the run.** The Origami step runs first in the team run, with up to 100 seconds of its budget: stops already approved, then replies, then Origami's own unsubscribes. Work it cannot finish in time is deferred to the next run and never counted as a failed attempt. The status scan reads up to 12 pages a run, each checkpointed, within its time slice.
- **Evidence.** Lead replies (`GET /send/replies?from=lead`) are saved page by page. An independent recent scan and a fresh first-page check run alongside the historical backfill; the completed cursor retains a 72-hour overlap because `since` is the reply's received time, not when Origami stored it. Status and sequence searches also checkpoint pages, so a long scan resumes on the next run. Origami's unsubscribes appear as `status: replied, stop_reason: unsubscribed`; the status scan reads each campaign's `replied` and `unsubscribed` people and periodically reads everyone. The webhook and the poll record a reply once, under the key `reply:<sequence>:<received time>`; a delivery's `webhook-id` is recorded in `gtm_origami_webhook_deliveries`. `gtm_origami_replies` keeps ids, the verdict and keyed hashes only, never a reply's text, an address or a profile URL, and `last_error` never holds an address, a slug or a Twenty error body. Origami does not document a status-change event ID or timestamp: an unsubscribe, re-consent, and another status-only unsubscribe on the same sequence cannot be distinguished if the intermediate state was never observed. An unchanged status is not treated as a new refusal, because doing so could overwrite later consent.
- **Rule `origami-reply-v1`** (`lib/origami/rule.ts`, deterministic, no model). Words are judged after removing quoted text, a leading greeting ("Hi John,", "Dear Ana,", "Bonjour,") and trailing sign-offs or a name. Confirmed: Origami's own unsubscribe, or the person's first reply on the sequence whose words are exactly no, no thanks, no thank you, not relevant, unsubscribe, remove me or stop. Possible: the same phrase later in a conversation; unsubscribe wording ("opt me out", "take me off", "please remove"); a clear refusal ("not interested", "thanks, but no", "nah", "not the right person"); refusals and unsubscribes in German, Dutch, French, Spanish, Italian, Portuguese, Swedish, Danish and Norwegian ("nein danke", "non merci", "no gracias", "nej tack", "abmelden", "désinscrire", "darse de baja", ...); a line that is only "no" or "stop"; or a reply of 25 words or fewer with a standalone no, nope, nah or stop that is not "no problem", "no worries" and the like. Over-flagging into possible is deliberate: a person reviews it. Anything else is recorded with no action. The shared email rule also holds a bare "no" (after a greeting too) as a possible opt-out.
- **Matching.** One Twenty person by address (primary or additional), else by LinkedIn slug. Zero or several is never guessed: the sequences still stop and a `suppression:origami_unmatched` incident asks a person to handle it in Twenty.
- **Consent write safety.** Before a Twenty write, the writer rechecks the evidence's keyed identity against the current person and checks that the identity still resolves uniquely. A missing or changed identity, an ambiguous match, or a CRM edit later than the relevant opt-out decision holds the write as failed for review. A generic CRM update timestamp cannot prove which field changed, so this deliberately holds some unrelated edits too; it never assumes they were not re-consent. Status-only evidence has no refusal timestamp and requires a human opt-out decision before changing consent. Existing unsubscribed consent is a no-op after the identity check.
- **What is applied.** Confirmed: `gtmMarketingConsent=UNSUBSCRIBED` plus an evidence line naming the Origami campaign, sequence, received (or, for an unsubscribe status, observed) time and rule, through the guarded Twenty writer, subject to the consent safety checks above. Possible: an `OPT_OUT_REVIEW` operation that holds email on the desk, no consent write. Either way, every live sequence of that person (same address or LinkedIn slug, draft, paused and active campaigns alike) gets a `sequence_stop` operation: read first (already stopped is success; a sequence with no steps yet counts as live), `POST /send/campaigns/{campaign}/people/{sequence}/stop`, then read back; it is confirmed only when Origami shows it can send nothing more. A stop is reversible in Origami. Every operation key carries its evidence id, so a new opt-out after a correction is applied again. Stops and eligible confirmed reply writes apply without a per-operation approval once the flag is on (John's decision, 2026-11-10); status-only consent and other safety holds require review. The flag also lets the Twenty writer apply eligible Origami operations, while email suppression operations still need `EMAIL_SUPPRESSION_APPLY=1` and their approval.
- **Reviews.** `gtm suppression origami-reviewed --ids <gtm_origami_replies ids> --by <name>` with `--opt-out` (adds the consent write, the stops carry on), `--not` (releases the desk hold and cancels stops not yet made; a sequence already stopped is resumed in Origami by hand) or `--handled` (no single Twenty person matched and it was dealt with in Twenty). Each records the person's decision and clears its incident.
- **Not covered.** A person enrolled in a new campaign after their opt-out is not stopped by this step; the campaign guard at enrollment is VIB-520.

**Recovering a held consent write.** Inspect the evidence and current Twenty identity and consent before acting. For unreviewed, matched status evidence, use `gtm suppression origami-reviewed --ids <evidence-id> --by <name> --opt-out` only after a person confirms the refusal is newer than any re-consent. If a decision was already reviewed and a later CRM edit leaves the write failed, an authorized person can decide and set the correct consent directly in Twenty; once the identity is again uniquely matched, the next writer run confirms an already-unsubscribed person without writing. If identity is changed or ambiguous, first resolve the correct person manually in Twenty; do not rebind the stale operation by guessing. Once its outcome has been handled, an operator may cancel that exact stale Twenty operation using the database procedure below. This leaves all Origami stops untouched and records the operator in the operation's audit field. Verify the affected row count is one; investigate if it is zero.

```sql
-- Replace only the operation id and operator name after inspecting the exact failed operation.
do $$
declare
  holder text := 'origami-manual-recovery-' || gen_random_uuid()::text;
begin
  if not public.gtm_take_lease('email.suppression.apply', holder, 600) then
    raise exception 'suppression writer is running; retry later';
  end if;
  update public.gtm_email_sync_ops
    set state = 'canceled', last_error = 'Manually resolved in Twenty by OPERATOR', updated_at = now()
    where id = OPERATION_ID and destination = 'twenty' and action = 'person_opt_out'
      and policy_version = 'origami-reply-v1' and state in ('approved', 'failed');
  if not found then raise exception 'operation was not an eligible open Origami consent write'; end if;
  perform public.gtm_release_lease('email.suppression.apply', holder);
end $$;
```

To pause, unset `ORIGAMI_OPTOUT_APPLY`: the webhook then acknowledges deliveries without work and the hourly step skips; the poll catches up from its cursor when it is set again.

Legacy private-archive Actions, including Sunday draft/smoke workflows, are disabled. Relocated private-hub workflow replacements remain manual and held behind false guards. There is no automatic Sunday drafting claim in this operating context; activating a held workflow is a separate authorized operation.
